# Art licensing — obligations and rules

IronLog bundles third-party artwork. This file records what that obliges us to
do. It is short on purpose: every rule here is one someone could break by
accident with a well-intentioned commit.

Background research: `../ART_LICENSING_RESEARCH.md`.
Machine-generated inventory: `art-coverage.md`, `../assets/art/manifest.json`.

Every harvested file was verified CC BY-SA 3.0 at ingest; the harvester aborts
on any licence outside its allow-list.

## The four rules

### 1. Never modify the bundled SVGs

They are byte-identical to what Commons served, and `manifest.json` stores a
sha256 for each. Unmodified artwork distributed alongside our code forms a
*collection* under CC's own terms, so **our source stays proprietary and
share-alike never reaches it**.

The markup is embedded as JS string literals in `src/data/art/` (generated by
`scripts/build-art-registry.ts`) rather than shipped as bundled asset files.
That is a container change, not a content change — the same bytes, the way a
file inside a ZIP is still that file — and `scripts/art.test.ts` asserts every
embedded string equals its source file exactly. Bundling them as Metro assets
was tried first and *breaks in release builds*; the reasons are documented at
the top of the generator.

Modifying one — recolouring, running svgo, normalising a viewBox, compositing
the two frames, re-tracing — makes that file **Adapted Material**, which must
then itself be released under CC BY-SA 3.0. Anyone could extract it from the
APK and demand the licence. Our code would still be unaffected, but the changed
image would not be ours to keep closed.

So: **no build step touches `assets/art/`.** Not svgo, not SVGR, not a
"convert to ImageVector" pass. `scripts/harvest-art.ts` explains why the ~4 MB
saving is not worth it.

### 2. Colour is applied at render time, never baked in

These files contain no `fill`, no `style`, no `<style>` block and no embedded
raster — verified across all 353 by `assertTintable()` in the harvester, which
fails the harvest if that ever changes. So `ExerciseArt.tsx` passes
`fill={palette.exerciseArt}` to `SvgXml` and gets full light/dark theming
without editing a byte.

This is the mechanism that makes rule 1 costless. Do not replace it with
pre-tinted asset variants.

**One further render-time fix, for the same reason.** Every file wraps its paths
in `transform="matrix(.1 0 0-.1 0 960)"`. That is valid SVG, but
react-native-svg's transform parser rejects the space-less `0-.1` and silently
drops the matrix, which loses the scale and Y-flip and renders the artwork
off-canvas — apparently blank. `src/domain/svgCompat.ts` inserts the missing
whitespace *in memory, on the way to the renderer*. The distributed bytes are
untouched, exactly as with the colour. Do not "fix" the files on disk instead.

### 3. The credits screen is generated, not hand-written

It is built from `assets/art/manifest.json`, which snapshots per-file licence,
artist, credit URL and Commons **file-page** URL at ingest. Commons files do get
deleted and relicensed, so the snapshot is the record of what we actually
shipped.

Artist strings are normalised in `scripts/commons.ts`: the category really
contains `Everkinetic`, `everkinetic` **and** a typo, `Everkineteic`. Without
folding them the same artist appears three times.

### 4. The EULA must not forbid extracting these assets

CC BY-SA carries a **"no additional restrictions"** term. A blanket
"all content in this application is proprietary" clause in our terms would
breach the licence for the bundled artwork.

Any terms-of-use text must carve out the CC BY-SA assets and say plainly that
recipients may extract and reuse them under CC BY-SA 3.0. This is the easiest
rule here to violate by pasting in a boilerplate EULA.

## If iOS is ever added

CC 4.0's anti-TPM clause is a live question on iOS, where Apple's FairPlay
encryption may count as an "effective technological measure"; it is **not** an
issue for Android, where Play signing is not DRM in that sense. Our files are
CC BY-SA **3.0**, whose equivalent term is worded differently, but get a legal
opinion before shipping these assets in an App Store binary. The usual
mitigation is publishing the exact asset set in a public repository so
recipients can obtain it unencumbered.

## What we deliberately did not use

From the research: `free-exercise-db` / `wrkout/exercises.json` (images **and**
instruction prose traced to bodybuilding.com), the entire GymVisual-derived
ExerciseDB/animated-GIF lineage, MuscleWiki, wger's laundered image licences,
and every Kaggle/HuggingFace image set.

**This is also why no exercise in `src/data/seed/` has instruction text.** The
widely-copied free-exercise-db descriptions are verbatim bodybuilding.com copy.
Exercise *names*, *equipment* and *muscle mappings* are fine to curate; how-to
prose must be written from scratch.
